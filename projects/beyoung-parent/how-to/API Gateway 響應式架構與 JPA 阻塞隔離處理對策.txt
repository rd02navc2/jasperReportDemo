================================================================================
Spring Cloud API Gateway 響應式架構與 JPA 阻塞隔離處理對策
================================================================================

一, WebFlux / Netty 運行層級關係 (由底向上)
--------------------------------------------------------------------------------
這套架構是現代微服務處理大規模請求進入系統時的標準配置:

  Spring Cloud Gateway (應用層)
  定義 Route (路由),Predicate (斷言) 和 Filter (過過濾器) 等網關業務邏輯
       |
       v (使用 Project Reactor 作為編程模型)
  Project Reactor / Mono & Flux (邏輯層)
  數據與操作的異步載體, 確保執行緒在等待 I/O 時可以立刻被釋放去處理其他任務
       |
       v (響應式核心框架)
  Spring WebFlux (中間層)
  封裝對底層通訊伺服器的調用, 並將請求/響應轉化為響應式流 (Reactive Streams)
       |
       v (高性能網絡通訊)
  Netty 伺服器 (底層運行環境)
  提供 Event Loop 機制, 用極少數的執行緒（通常等於 CPU 核心數）處理極大量的並發連接


二, 錯誤示範：直接在 WebFlux 呼叫 JPA 的卡死連鎖反應
--------------------------------------------------------------------------------
當直接執行傳統阻塞操作（如：Mono.just(repo.findAll()) 或直接回傳 List）時的災難現場：

  [ 前端高並發請求流入 ] ---> 抵達 Netty Event Loop 執行緒 (少數的交警執行緒)
                                    |
                                    v
                        直接呼叫 jpaRepository.findAll()
                                    |
                                    v (錯誤發生)
                        交警執行緒被迫在原地「搬磚」 (同步阻塞等待 DB 回傳)
                                    |
                                    +---> [ 執行緒池被耗盡 ] ---> 新請求進來無人調度
                                    +---> [ 舊請求出不去 ] ---> 記憶體與連接堆積
                                    |
                                    v (終端結果)
                        Postman / Client 畫面持續轉圈圈，最終超時 Halt 住 (癱瘓)


三, 正確解決方案：使用專屬執行緒池隔離阻塞代碼 (黃金律法)
--------------------------------------------------------------------------------
"永遠不要在 Netty 的 Event Loop 執行緒中執行任何會 Block 的操作!"
透過自訂的獨立執行緒池 (如 jpaScheduler), 將阻塞壓力自核心 Event Loop 中完全抽離;

  [ 前端 HTTP 請求 ]
       |
       v
  Netty Event Loop 執行緒 (僅做請求接收與快速調度)
       |
       +---> (1) 使用 Mono.fromCallable() 或 Mono.defer() 包裹阻塞操作 (延遲執行)
       |
       +---> (2) 呼叫 .subscribeOn(jpaScheduler) 或 Schedulers.boundedElastic()
       |
       v (執行緒安全切換, Event Loop 立即被釋放, 回頭處理下一個請求)
  
  自訂隔離執行緒池 (如：jpaScheduler / 大小為 50 的專屬池)
       |
       +---> (3) 在此執行緒執行 jpaRepository.findAll() (阻塞搬磚由它承擔)
       +---> (4) 取得資料庫回傳結果，並封裝回 Mono/Flux 流
       |
       v (異步回流)
  網關響應式鏈條 ---> [ 經由 Web Handler & Filter Chain ] ---> [ Netty 發回回應 ] ---> HTTP 200 OK
