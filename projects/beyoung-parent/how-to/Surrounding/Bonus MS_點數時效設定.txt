## Redis 測試驗證步驟（快取清除與防禦驗證）
--------------------------------------------------------------------------------
由於前線 POS 在執行加點時會查詢行銷活動專案 (LrqFile) 並將規則暫存於 Redis 中,
為了驗證當排程將過期點數歸零,或營運人員動態調整活動效期時, 快取與排程不會發生時空衝突,
請依循以下步驟進行測試驗證：

1. 模擬快取環境建立
   透過後台或 API 新增一筆即將過期的行銷專案規則（例如專案代碼 701, 客製代碼 603）;
   使用前線 POS 任意發起一筆加點請求，迫使系統執行 marketingProjectService.getValidProject,
   此時活動規則將會成功寫入 Redis;
   驗證指令：
   redis-cli > KEYS *marketing*
   redis-cli > GET "marketing:project:701:603:A101"
   
透過後台或 API 新增一筆即將過期的行銷專案規則（例如專案代碼 702, 客製代碼 702）
  http://localhost:8095/Surrounding/api/bonus/Marketing/addProject

   驗證指令：

   此時持該活動專案代碼再次發起 POS 加點請求;
   驗證結果：
   系統應精準拋出 IllegalStateException 或 IllegalArgumentException（訊息: 活動時效不符政策）;
   前台 POS 應正確收到 400 Bad Request, 且資料庫不應產生 any 新的加點 BONUS_LOG;

5. 驗證分散式最終一致性（T+1 半夜自動對帳）
   當下游 Member 微服務也模擬接收 Kafka 事件落庫後，執行跨庫對撞 SQL 驗證兩邊欄位完全對齊：
   SELECT 
       b.id AS bonus_log_id,
       b.card_no,
       b.point AS bonus_point,
       m.source_bill_no,
       m.changed_point AS member_point
   FROM bonus_sf.BONUS_LOG b
   LEFT JOIN member_sf.member_point_journal m   //dc- 沒有member_sf.member_point_journal!
       ON CONCAT('EXPIRED_BILL_', b.id) = m.source_bill_no
   WHERE b.access_id = 'SYSTEM_CRON_JOB' AND b.card_no = 'CARD_TEST_999';
   (預期結果：兩邊單號完全對撞契合，且 bonus_point = -500, member_point = -500，無 any 漏單與不一致)
