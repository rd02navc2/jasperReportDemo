### 活動專案永久變更門檻與大額滿額贈點成功閉環測試

步驟 1：營運後台調整活動持久化門檻
使用 Postman 呼叫行銷控制層 API，將 702 活動專案的門檻金額持久化修改為 50000 元;
PUT
http://localhost:8095/Surrounding/api/bonus/Marketing/updateProject
JOSN
{
  "lrq01": "702",
  "lrq02": "702",
  "lrqplant": "A101",
  "lrq03": 50000,
  "lrqacti": "Y",
  "lrq10": "2026-05-01",
  "lrq11": "2026-06-03"
}

預期結果：回傳 HTTP 200 OK，回傳的實體中 `lrq03` 為 50000;
檢視 MySQL：SELECT lrq03 FROM lrq_file WHERE lrq01='702' AND lrq02='702' AND lrqplant='A101'; 欄位值已變更為 50000;
進入 Redis 執行 `AUTH <密碼>` 後，執行 `KEYS *702*` 應確認原專案快取已被精準強刷清除;

步驟 2：【前線發送符合新門檻之結帳請求】
    開啟 Kafka 監聽 `bonus-out-0`;隨後模擬一筆金額為 35000 元（已高於新設定的 30000 元門檻）的線上訂單;
   *HTTP 方法：POST
   *URL：http://localhost:8095/Surrounding/api/bonus/Point/addPoint
   *Body (JSON)：
      {
        "center": "A101",
        "counterId": "CT001",
        "cardNo": "VIP888999",
        "amount": 35000,
        "orderNo": "ORD202606060001",
        "point": 70,
        "lrq01": "603",
        "lrq02": "603"
      }
   *預期結果：回傳 HTTP 200 成功;系統 Log 顯示：`【規則引擎】金額達標！專案: 603-603 ... 執行加贈 500 點流程`;

步驟 3：【數據審計與 Kafka 異步校驗】
   *數據庫校驗：
      執行 SQL：`SELECT*FROM bonus_log WHERE access_id = 'VIP_GIFT_ORD202606060001';`
      預期結果：必須成功查到一筆加贈紀錄，且其 point 欄位值為 500;
   *Kafka 事件校驗：
      預期結果：`bonus-out-0` 頻道收到通知，事件體內的關聯單號為 "VIP_GIFT_ORD202606060001"、點數為 500;

--------------------------------------------------------------------------------
【情案二：大額贈點冪等性防重複消費贈點測試（Idempotent Case）】
--------------------------------------------------------------------------------
步驟 1：【模擬網路超時、重試發送相同請求】
    維持現有設定;使用與【情案一】**完全相同**的 JSON 內容（訂單號維持 ORD202606060001），再次對 `/addPoint` 發送一次 POST 請求;
   *預期結果：API 依然回傳 HTTP 200 成功（避免前端 POS 拋出中斷錯誤）;
    
步驟 2：【帳務防線查驗】
   *數據庫校驗：
      執行 SQL：`SELECT COUNT(1) FROM bonus_log WHERE access_id = 'VIP_GIFT_ORD202606060001';`
      期結果：Count 數量必須為 1，絕對不得變成 2（確認成功被 `existsByAccessId` 冪等性機制攔截）;
   *記錄檔校驗：
      預期結果：Log 應印出 `[點數攔截]` 或直接被攔截 Return，未重複執行 `bonusLogRepository.save` 與 Kafka 發送;

--------------------------------------------------------------------------------
【情案三：未達綁定動態門檻退回常規累點測試（Fallback Case）】
--------------------------------------------------------------------------------
步驟 1：【發送未達標結帳請求】
    目前 603 專案在 MySQL/快取 中的門檻為 30000 元;發送一筆交易金額僅為 12000 元的線上訂單;
   *HTTP 方法：POST
   *URL：http://localhost:8095/Surrounding/api/bonus/Point/addPoint
   *Body (JSON)：
      {
        "center": "A101",
        "counterId": "CT001",
        "cardNo": "VIP888999",
        "amount": 12000,
        "orderNo": "ORD202606060002",
        "point": 24,
        "lrq01": "603",
        "lrq02": "603"
      }
   *預期結果：回傳 HTTP 200 成功;

步驟 2：【決策閘道分流校驗】
   *數據庫校驗：
      執行 SQL：`SELECT*FROM bonus_log WHERE access_id = 'VIP_GIFT_ORD202606060002';`
      👉 預期結果：查無此資料（金額未達標，不給予大額加贈）;
   *常規校驗：
      👉 預期結果：系統自動導向 `addPoint` 常規流程，依活動 603 計算並寫入標準 LSM 流水帳（發放原有的 24 點）;Log 顯示：`【規則引擎】未達滿額加贈門檻，執行常規 603/603 累點邏輯`;

--------------------------------------------------------------------------------
【情案四：異常參數與專櫃黑名單防禦測試（Robustness Case）】
--------------------------------------------------------------------------------
步驟 1：【測試黑名單專櫃攔截】
    傳入一個已被列入 `exclude_counter_file` 排除名單的專櫃代碼（例如: BLK99）;
   *HTTP 方法：POST
   *URL：http://localhost:8095/Surrounding/api/bonus/Point/addPoint
   *Body (JSON)：
      {
        "center": "A101",
        "counterId": "BLK99",
        "cardNo": "VIP888999",
        "amount": 55000,
        "orderNo": "ORD202606060003"
      }
   *預期結果：系統精準阻斷交易，回傳 HTTP 400 Bad Request;
                錯誤訊息提示包含：`此專櫃為排除專櫃`，全鏈路不執行任何資料庫寫入;
